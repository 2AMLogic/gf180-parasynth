# R2: pulse2x, the scheduling saving, the #354 ladder repair and #315

**Status: RELEASE CANDIDATE, built and bound** (`fpga/release/r2-2025.1.json`,
`r2_release.py`, T-RELEASE-BOUND-R2). pulse2x is in R2 by **operator override** of its
acceptance rule, not by passing it (see Known limitations). R2 differs from R1's freeze in
exactly the reviewed set below: `voice_dp.v`, `polyblep_saw_pair.v`, `ladder_dp_n.v` and
the Arty XDC. R1 (`fpga/release/R1.md`, `r1-2025.1.json`) stays published and is the
**rollback**; R0's and R1's records are byte-untouched. No physical programming, control
or audio capture has been performed on R2.

## What R2 changes

**The settled set (#282, plan099 §6).** Nothing else goes in: pulse2x at 0.74 rectangle
headroom, the scheduling saving, the #354 repair and #315. No preset changes are confirmed,
so R2 plays R1's presets and R1's frozen kit. R2 lands as the next engineering release; it
does not declare the sound goal complete, and the sound queue carries on.

## Known limitations (operator override, not a pass)

The pre-declared acceptance rule for pulse2x (candidate vs R1, a 1.00 dB band, frozen at
`d1fe013`) gives **NOT ACCEPTED: 6 of 107 untouched conditions fail**
(`docs/scorecard/m5-artifacts-333/README.md`, record `r2-compare/r2-074.json`). The one
bounded repair also failed (PR #370). **The operator included pulse2x in R2 anyway**
(#282, 2026-09-27), accepting the trade-off below. That verdict stands; R2 does not pass
the rule, and nothing in this release says it does.

| condition | failing property | R2 − R1 |
|---|---|---:|
| square, MIDI 36, cutoff 400, q 0.5, drive 1.6 | brightness (upper wanted) | −4.82 dB |
| pulse29, MIDI 36, cutoff 400, q 0.5, drive 1.6 | brightness | −3.46 dB |
| square, MIDI 96, cutoff 20 kHz, q 0.5, drive 1.6 | brightness | −2.46 dB |
| pulse29, MIDI 96, cutoff 20 kHz, q 0.5, drive 1.6 | brightness | −2.45 dB |
| pulse29, MIDI 84, cutoff 400, q 0, drive 1.6 | brightness | −1.64 dB |
| pulse29, MIDI 120, cutoff 400, q 0.5, drive 0.75 | absolute / relative unwanted energy | +1.35 / +2.92 dB (at −113 dBFS, near-silent) |

- **Gained:** M5A/M5B foldback 10.27/8.85 dB → 2.21/1.91 dB, within the 3 dB limit; 6.41/5.28
  dB of that is beyond the level change (the level-only control accounts for 1.66/1.65 dB).
- **Lost:** five extreme rectangle patches, all at drive 1.6 with resonance 0.5 or cutoff 400,
  are darker than R1 by 1.6 to 4.8 dB (the 0.74 rectangle drives the tanh ladder about 2.6 dB
  less hard). One near-silent point has more unwanted energy.
- **Open follow-up:** whether R1's brightness at drive 1.6 is character or alias-driven
  saturation is a measurement against the Minimoog reference, not settled here.
- **Rollback:** a player who prefers R1's sound at those settings loads R1 (`--image r1`).

Check it (BOUND / STALE / REFUSED), or as a trial with its two STALE controls:

```sh
.venv/bin/python fpga/release/r2_release.py
python tools/trial.py run T-RELEASE-BOUND-R2
```

The controls are the confusions this release invites: the R2 manifest naming
**R1's image** (`stale-r2-image`: the PULSE2X=1 release bound to the PULSE2X=0
bitstream) and naming **R0's host bytes** (`stale-r2-host`). Each must be STALE
at exactly the substituted fields while the unmodified copy is BOUND.

Program it (volatile), then use the R1 quick-start with `--image r2`:

```text
openFPGALoader -b arty_a7_100t fpga/reports/arty/r2-2025.1/arty.bit
.venv/bin/python fpga/uart_host.py --port /dev/cu.usbserial-XXXX run --fixture demo --image r2
.venv/bin/python fpga/midi_session.py --port /dev/ttyUSB1 --midi-in /dev/snd/midiC1D0 --image r2
```

**`--image r2` sends exactly R1's bytes** for every supported command (R2 has no
kit or preset change; `fpga/test_named_r2.py`, and `r2_release` checks it against
R1's bound bytes). The host therefore cannot tell R1 from R2 by what it sends,
and cannot read the image back: which image is on the board is declared, not
verified. The default stays `release` (R0).

## What changed in the release machinery (and what did not)

- **R0 and R1 records are byte-untouched**: `baseline-2025.1.json`,
  `r1-2025.1.json`, `r1-candidate.json`, `r1-kit.json` and both publication
  directories. Both still check BOUND.
- The tree's image is now R2 (`build_arty.TREE_IMAGE`): the builder defaults to
  `--image r2`, and the publisher's wrapper binding (`VERIFICATION_BY_WRAPPER`,
  checked by T-RELEASE-BOUND's `arty-evidence-binding`) names `r2-clean`. R1's
  sources are frozen at `6864435`; an `--image r1` build of this tree refuses at
  its verification record rather than labelling R2's RTL with R1's configuration.
- The publisher binds each image to its own configuration and proof;
  `r1_release`'s image and ext-I/O checks take another image's parameters and
  default to R1's (R1 re-checks BOUND through them).
